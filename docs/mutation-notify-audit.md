# Mutation-notify audit — §1.1 of `brief-phantom-mutations.md`

**Every payload key the reducer applies, probed against the state on both sides of its own event.**
Generated by `wb mutations` over the reference panel (5 seeds, 50 years) — re-run it rather than
trusting this transcript. The table below is the **post-repair** state; the one finding it was
commissioned to look for is fixed, and the figures the repair changed are named in §1 of
`docs/phantom-mutations-report.md`.

**Why an audit rather than the one fix.** This is the third instance of one shape.
`GoalBook.Remove` notified its watcher whether or not the book held the goal and produced fifteen
phantom endings in 477; the relation graph then did the same thing with severances, and a declaration
of war in year 38 claimed to break a pact that had ended in year 27. Two instances is a coincidence
and three is a family, so what this measures is every mutation key rather than the one that was
found.

**Not reasoned from the call sites.** §4 of the project reference records what happens when a
measurable property of the code is written out by hand: the list of rules lacking floor protection
named two that were protected and omitted one that was not — wrong in both directions. So this reads
the component each key names before and after the reducer applies it and asks whether it moved.
`PhantomMutationTests.TheAuditProbesEveryKeyFamilyTheReducerApplies` holds the audit's family list
against the reducer's own `switch`, so a key family added to one and not the other fails a test
rather than being skipped in silence.

**Pre-repair, for the record:** `relDel` had 132 keys of which **14 named no live edge**, all on
`DIPLO.WAR_DECLARED`. Every other family was already clean of that verdict. It is 118 keys and zero
now, and no real severance was lost.

**Two sites, one repaired.** The `no entity` column holds the second: `LIFE.DEATH_VIOLENT` writes
`leg:-` where the victim belonged to no house, twice across the panel, and the reducer drops it in
silence because `leg:-` has two tokens where its case wants three and so matches nothing at all. Not
repaired at ruleset 8, and the reason is in `EventDraft.Delta`: guarding it belongs where every delta
passes rather than where severances are written, which puts it beyond the reach of the severance
off-switch and would cost rulesets 5, 6 and 7 their byte-level reproduction. `PhantomMutationTests`
asserts the count is exactly two, so it cannot spread while it waits, and a repair has to bring the
number down deliberately rather than slipping past.

## Mutation-notify audit — does every key that asserts a change make one?

5 world(s): seed 1 (760 records), seed 7 (594 records), seed 42 (954 records), seed 1234 (897 records), seed 2025 (772 records).

**Every payload key the reducer applies is probed on both sides of its own event.** A key is `real` where the component it names moved, and idle where it did not. Idle splits four ways, and only the first is the `GoalBook.Remove` family:

- `no referent` — the key names something the state does not hold. A claim about a tie that is not live or a goal that has gone. **This is what ruleset 8 repaired.**
- `no entity` — the key names the null id, which prints as `-`. A different defect with a different repair, and not fixed at ruleset 8: it does not parse into the shape its reducer case wants, so it is dropped a step earlier. Bounded by a test rather than left to grow.
- `already there` — the referent exists and is already in the state the key asks for.
- `absorbed` — the delta is real and a floor or ceiling takes all of it. A property of the quantity rather than a false claim, and reported apart for that reason.

### One key, written twice into one event

**616 key(s) appear more than once in their own event**, across 278 event(s). Found by this audit rather than looked for: the probe read an edge as unchanged across an event carrying two deltas for it, and the two cancelled.

**Not a phantom mutation.** Every occurrence is a real delta and the reducer applies them in order, so the world is right, and both survive a round trip because `Event.Data` is an ordered list and `JsonDocument` keeps duplicate property names. What is wrong is the record: one event states two opposite changes to one edge, any reader fetching the key by name sees only the first, and the written JSON carries a duplicate object key that most parsers outside this repository resolve as last-one-wins.
